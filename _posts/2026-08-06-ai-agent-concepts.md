## 什麼是 AI Agent

簡單說，AI Agent 是「能自己決定下一步該做什麼、並且會採取行動的 LLM 系統」。跟單純問一句答一句的 Chatbot 最大的差異在於：Agent 會在得到目標之後，自己拆解步驟、呼叫外部工具、觀察結果，然後決定要不要繼續下一步，直到任務完成。

一個常見的比喻：Chatbot 像是「問路的人」，你問一句它答一句；Agent 更像是「幫你跑腿的人」，你只要交代目標（例如「幫我訂週五飛東京的機票」），它會自己查航班、比價、確認你的偏好、最後完成訂票，中間發生什麼事你不用一步步下指令。

## 跟傳統 LLM 對話的差異

| | 一般 LLM 對話 | AI Agent |
|---|---|---|
| 互動模式 | 一問一答，人類主導每一步 | 給定目標，Agent 自主規劃多個步驟 |
| 是否能行動 | 只能生成文字 | 能呼叫工具、執行動作、讀寫外部系統 |
| 是否有記憶 | 通常只有單次對話的上下文 | 可能有短期＋長期記憶機制 |
| 是否會自我修正 | 不會 | 會根據執行結果調整下一步（甚至重試） |

## 核心組成元件

一個典型的 Agent 系統，通常由這幾塊組成：

1. **LLM / 大腦（Planner）**：負責理解目標、拆解任務、決定下一步動作
2. **Tools（工具）**：Agent 能呼叫的外部能力，例如查資料庫、呼叫 API、讀寫檔案、執行程式碼
3. **Memory（記憶）**：
   - 短期記憶：當前任務的對話歷史／中間結果
   - 長期記憶：跨任務、跨 session 保留的知識，通常用向量資料庫（RAG）實現
4. **Executor（執行器）**：實際去呼叫工具、拿到結果，並把結果回饋給 LLM
5. **Orchestrator（協調層）**：管理整個迴圈的進行、終止條件、錯誤處理、有時還包含多個 Agent 之間的協作

## Agent Loop：運作的核心模式

最常見的運作模式是 **ReAct（Reason + Act）**：模型交替進行「推理」與「行動」，每一輪都會：

1. **觀察（Observe）**：看目前的狀態與上一步的執行結果
2. **思考（Reason）**：判斷距離目標還缺什麼，決定下一步要做什麼
3. **行動（Act）**：呼叫工具或給出最終答案
4. 重複以上步驟，直到任務完成或達到終止條件

用虛擬碼表示大概是：

```
while not done:
    observation = get_current_state()
    thought, action = llm.decide(observation, history)
    if action == "final_answer":
        done = True
    else:
        result = execute_tool(action)
        history.append(thought, action, result)
```

除了 ReAct，還有幾種常見的規劃策略：

- **Plan-and-Execute**：先一次規劃出完整的步驟清單，再依序執行，跟 ReAct 這種「邊做邊想」的方式相對
- **Reflection（自我反思）**：Agent 在得出結果後，先自我檢查是否合理，不滿意就重新來一輪
- **Tree of Thought**：同時展開多條思考路徑，比較後選出最好的一條，適合需要探索多種可能性的任務

## Tool Calling（工具呼叫）

這是 Agent 能「行動」的關鍵機制。現在主流 LLM API 都支援讓開發者定義工具的 JSON Schema（名稱、描述、參數格式），模型會根據對話內容判斷要不要呼叫、呼叫哪一個、帶什麼參數。開發者這邊要做的事：

- 把系統既有的功能包裝成「模型看得懂」的工具描述（清楚的名稱與參數說明很重要，會直接影響模型呼叫的準確度）
- 執行模型要求的呼叫，並把結果（成功或錯誤）回饋給模型
- 設計終止條件，避免模型陷入重複呼叫的迴圈

## Memory 與 RAG

單次對話的 context window 是有限的，任務一長就會超出範圍。常見的解法：

- **對話摘要**：定期把久遠的歷史壓縮成摘要，保留關鍵資訊、丟掉細節
- **向量檢索（RAG）**：把長期知識存進向量資料庫，需要時才檢索相關片段塞進 context，而不是整包記憶都放在對話裡

## 常見的協定與生態系

- **Function Calling / Tool Calling API**：各家 LLM 供應商提供的標準化工具呼叫介面
- **MCP（Model Context Protocol）**：讓工具/資料來源可以用統一協定被不同的 Agent 或應用呼叫，解決「每個工具都要重新接一次」的問題
- **Multi-Agent 框架**：讓多個各司其職的 Agent 互相溝通協作（例如一個負責規劃、一個負責執行、一個負責審核），處理更複雜的任務

## 常見挑戰

- **幻覺（Hallucination）**：模型可能自己編造工具不存在的參數或結果，需要驗證機制
- **無限迴圈 / 失控**：規劃不收斂時會一直嘗試，要有明確的終止條件與上限
- **成本與延遲**：多輪推理＋多次工具呼叫，token 消耗跟延遲會比單次問答高很多
- **安全性**：Prompt injection、工具被誤用執行危險操作，需要在工具層做好權限控管與輸入驗證
- **可觀測性**：多步驟的決策過程不透明，除錯需要完整記錄每一輪的思考與行動（tracing）
